# Authentication

Pages CMS uses Better Auth's SQLite adapter with the existing user, session, account, and verification identities. Authentication is request-scoped: configuration, database, and session services are initialized lazily and reused for the duration of one request.

## Local setup

Copy the example Worker variables and replace its placeholders:

```bash
cp .env.example .env.local
pnpm db:migrate
pnpm dev
```

`BETTER_AUTH_SECRET` must contain at least 32 characters. `BETTER_AUTH_URL` is the canonical local origin and fallback; local development also accepts the active `localhost` port selected by Vite. `DATABASE_URL` supplies local SQLite or remote libSQL/Turso application storage. Local development and the database schema migration scripts load `.env.local` automatically. Confirm that the target is disposable or backed up before applying migrations.

GitHub sign-in is enabled when both `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_CLIENT_SECRET` are present. Configure the GitHub callback URL as:

```text
http://localhost:3000/api/auth/callback/github
```

Replace `3000` with the active Vite port when it differs. Better Auth accepts the active localhost port, but GitHub requires the callback URL to match it exactly.

Google sign-in is enabled when both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are present. Create a web application OAuth client with the exact callback `<BETTER_AUTH_URL>/api/auth/callback/google`. Use separate Google Cloud projects for Local, Staging, and Production, as required by [Google's deployment-tier policy](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance). Staging uses `https://staging.pagescms.org/api/auth/callback/google`. Request only `openid`, `email`, and `profile`; Google sign-in does not grant GitHub repository access. Repository access still requires a linked GitHub account or an authorized collaborator membership.

Email-code sign-in is enabled when a trusted build-time plugin creates an email provider from the runtime environment. The bundled Resend plugin activates when both `RESEND_API_KEY` and `RESEND_FROM_EMAIL` are configured. A deployment can remove it and install a custom provider without changing authentication. See [`plugins.md`](./plugins.md).

Run `pnpm db:migrate` after updating a local checkout with new database migrations. Sign-in uses the shared database rate limiter and requires its schema.

The sign-in page uses the supported browser language or the configured instance default language. A saved account language takes priority for signed-in users. OTP emails use the sign-in language, and collaborator emails use the recipient's saved language or the configured instance default.

## GitHub App registration

```sh
pnpm setup:github-app
# Preview without opening GitHub, creating an App, or writing files:
pnpm setup:github-app --base-url cms.example.com --dry-run
# Local development needs a public webhook relay, e.g. a Smee channel:
pnpm setup:github-app --mode local --base-url http://localhost:3000 --webhook-url https://smee.io/your-channel
```

The Clack CLI asks for environment, application URL, unique App name, App owner, installation visibility and optional template creation, then displays a configuration summary before opening GitHub. Production is the default and requires a public HTTPS origin. Bare domains are normalized to HTTPS. A local application URL is accepted only in explicit local mode, with a separate public HTTPS webhook URL. Forward that endpoint to the local `/api/webhook/github` route; a Smee channel needs its relay running. GitHub cannot deliver webhooks to localhost or private addresses.

GitHub approval returns to `127.0.0.1:8787` on the computer running the CLI. This registration handoff is separate from the application OAuth callback and public webhook. Run the command on the same computer as the browser, or forward the callback port. `--port` changes the port; `--no-open` prints the browser URL instead of opening it. Ctrl+C cancels the listener. `--owner-type org --org my-company` chooses an organization. Private Apps install only on the owning account; choose public visibility or `--public` to allow installation elsewhere.

The CLI offers env-file output or copyable terminal values. File output asks for a location: production defaults to `.env.production.local`, local development to `.env.local`; `--env <path>` selects a path directly. `.env.production.local` is Vite’s ignored production-mode override convention, not a universal deployment requirement. Production's file is a staging location for deployment credentials: configure the saved variables in the host's secret store or server environment. The Node development scripts load `.env.local`, not the production file. Cloudflare secrets still belong in Worker bindings/secrets. The helper does not deploy or modify an existing registered App.

No seed database, pre-created App or API token is needed. GitHub provides the App ID, private key, OAuth credentials and webhook secret. A new file starts from `.env.example`, preserving comments and other settings without changing the example. Every existing file requires a separate update confirmation, even if it has no App ID. Noninteractive updates require `--overwrite`; `--yes` alone is insufficient. Managed keys are merged, including multiline PEMs and duplicate declarations; unrelated values and comments remain. A file changed during GitHub approval is rejected instead of updated. Missing authentication/encryption secrets and public placeholder values are replaced with random secrets; real existing keys remain. Files are owner-only. Secrets are printed only when the user chooses terminal output (`--output terminal`) or explicitly accepts manual recovery after a file-save failure. Terminal values are plain dotenv assignments without decorative prefixes so they can be copied intact. Terminal output writes no file. Confirm that `CRYPTO_KEY` matches any database containing existing encrypted installation credentials.

For unattended use, provide `--base-url` and `--yes`; a localhost URL still requires `--mode local` and `--webhook-url`. Unknown flags, missing values and invalid environment/URL combinations fail before opening a browser. `--help` lists options. Creating a new App updates managed credentials in the chosen output file only after review; existing-file updates additionally require confirmation or `--overwrite`. The helper never updates the old registered App.

Template-based repository creation is an explicit additional choice. `--templates` adds Administration write, the permission documented for [creating a repository from a template](https://docs.github.com/en/rest/repos/repos#create-a-repository-using-a-template). GitHub's manifest registration currently rejects `repository_creation`; the CLI omits that key rather than escalating the default grant. Without template creation enabled, existing repositories remain editable; the template-creation operation cannot succeed until the appropriate creation permission is separately configured and approved. Review the [manifest contract](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest) for manual setup. Disable user-to-server token expiration in the new App's settings if enabled, then install on the intended accounts/repositories.

## Runtime behavior

The sign-in page uses a centered 280px form titled “Sign in to Pages CMS,” with the shared logo in the top-left corner. Email-code verification retains the same width, and the loading placeholder matches that layout.

The home page, repository sidebar and Account page share the same compact 192px user dropdown. Its label shows a foreground medium-weight name above a smaller muted email, truncating long identities within the menu. It starts with that identity label and a separator, then Admin for verified deployment administrators, Account, Theme and Help, followed by a separator and Sign out. About opens from the logo rather than a user-menu item and restores focus to the logo when closed. The header menu opens downward, aligned to the right; the repository footer menu opens upward, aligned to the left. Repository navigation reuses the authentication query's server-derived admin flag; it does not fetch project discovery or account settings to populate the menu. The Account page, loading state and browser title use the same label.

A GitHub user token must establish write access before it can be used for repository reads or mutations. Mutation admission checks the provider and pins a known repository identity. A bounded, credential-hashed hint can select the installation path previously used for this repository; it contains no token or authorization grant. Every installation-backed mutation checks current collaborator membership and applies policy for its branch, resource, and path. A user-token rejection may retry a single-write operation once with installation credentials after fresh membership and policy checks. Conflicts, ambiguous failures, rate limits, completed writes, multi-write renames, and external uploads do not trigger automatic credential retries.

## Profile confirmation

New accounts must confirm their profile once after authentication. `/onboarding` prefills the provider’s name and picture where available, requires a nonblank display name of at most 120 characters, and displays the verified sign-in email read-only. The card contains three horizontal fields: Picture, Display name and Email, without field descriptions or a GitHub-account row. The optional picture appears first; its shared removal control is a muted ghost trash button in onboarding and Account. The authentication query no longer performs a provider lookup solely for confirmation. Existing completed accounts bypass confirmation. The existing `user.onboarding_completed_at` timestamp records the first valid profile save and stays unchanged on later saves; no separate welcome-dismissal state is used.

Protected page guards reuse the cached authentication query and preserve safe relative return destinations, including direct repository/entry links. Profile completion updates name, picture (if changed) and the marker in one account-scoped database operation. Account settings uses the same picture control afterward: picture changes save immediately, while display name changes require Save. GitHub synchronization continues to update GitHub identity, while subsequent provider sign-ins and links preserve confirmed display names and picture choices.

The avatar is the picture-upload button and single-file drop zone in confirmation and Account. Hover, keyboard focus and file drag reveal a faint ImageUp overlay; preparation and Account picture saving show a spinner. The trash control is muted at rest and uses foreground color on hover. It appears only for a selected picture. Account asks for confirmation before removing a picture and saves the removal immediately; onboarding holds picture changes locally until Continue. Neither view has picture Undo. Account displays the last confirmed picture until the server accepts a replacement or removal. Failed saves retain that confirmed picture, mark the picture control invalid and offer Retry in the error toast; editing the name does not silently retry a failed picture change. An unchanged gradient has no trash control. Account picture validation reports errors through Sonner and marks the control invalid; onboarding keeps its inline validation. Multiple dropped files are rejected. Picture uploads accept PNG, JPEG and WebP source files up to 5 MB. The browser center-crops and resizes them to 256×256 WebP, stripping source metadata. The server independently validates the raster format, signature and 100 KB encoded-image limit before storing the small data URL in the existing profile image column. Arbitrary remote image URLs remain rejected. This uses no repository writes or external avatar-upload service.

Projects empty states remain available regardless of profile completion. GitHub users without installations get an Install GitHub App action; installations with no available repositories offer Manage repository access and templates. Email/Google users without memberships see the email a project owner must invite. Search misses offer Reset search rather than setup instructions. GitHub connection state comes from the linked account, not the cached username; discovery reuses its existing credential lookup. Profile saves patch cached authentication, Account and Projects user details without refetching repository access. All Empty blocks are text-only and borderless, with foreground titles, muted descriptions and small action buttons. “Confirm your details” uses the shadcn Card components with default header spacing, a muted read-only email, no application header and a right-aligned Continue button with a trailing arrow in CardFooter. The former generic welcome and dismissal endpoint have been removed.

Switching project accounts keeps the account selector and search visible, replacing only the repository list with announced skeleton rows while an uncached account loads. Cached accounts display their own results immediately. Previous search results and failed-search fallback rows stay scoped to the same owner and installation; another account's repositories never act as placeholders. Searching within an account retains its rows with the existing filtering indicator and retry behavior.

Repository discovery follows the previous version: all-repository installations use GitHub’s repository search with `in:name`, the selected `user:` or `org:`, and `fork:true`, returning five results sorted by most recently updated. Search runs after a 500 ms debounce. These searches do not enumerate or cache the installation’s repository inventory. Selected-repository installations load their allowed list and filter names locally; collaborator-only accounts also filter their memberships locally. Only writable GitHub repositories are displayed.

Account renders all sections on one page. Deployment-owned `ui.accountSettings` arrays contribute unique anchor IDs, labels, optional ordering and lazy components receiving `{ accountId }`. Hosted supplies Email updates, Billing and API & MCP sections. OSS has no product-news signup UI, consent API, newsletter flag, or active consent columns. Authentication/invitation email delivery remains generic infrastructure.

Account editing preferences use a validated `user.preferences` JSON object. Server updates change only supplied JSON paths, preserving other settings during concurrent edits. Both account reads and writes verify the signed-in account and apply account access policy. The client scopes its query cache to the account, updates after confirmed writes, refreshes on focus, and retains the previous choice after failure. Translation initialization may fall back to Ask when preference reads fail; persistent read errors remain visible in Account.

Consent version `2026-10-21-v3` identifies the current wording. Version `2026-10-21-v2` was “Email me about new features and releases.” The original `2026-10-21` wording was “Email me product updates and release news.” Existing consent records retain their saved version.

## Account changes and deletion

Account saves valid name edits one second after typing pauses; blur, Enter and navigation within the app flush the current name. The field is a plain Input with no Save button, Input Group, success icon or visible status. Pictures save immediately after upload or confirmed removal. A successful current name or picture change shows “Profile updated” only after the server accepts it; an older name response does not announce success over newer typing. Repeated notifications for the same account and control replace the existing toast. Validation and request failures use the control’s standard invalid state and an error toast, with accessible error text retained for assistive technology instead of a visible inline message. Invalid names remain editable and are never sent to the server. Failed requests offer Retry in Sonner; name edits or another blur can also retry. Failed picture values are retained for retry while the last confirmed image stays visible. Inputs remain editable during name saves. Account warns before reloading or closing while profile changes are unsaved, saving or processing. Account-scoped controllers serialize writes, retain newer edits and pending saves across in-app navigation, and clear drafts and suppress notifications when the signed-in account changes. A full reload discards unsaved browser-memory drafts. Failed saves do not loop automatically; different changes already queued during that request still get their own attempt. Picture saves do not shorten a typing debounce. Profile responses update cached authentication, Account and Projects details without refetching repository access. Onboarding retains its explicit Continue submission and inline validation.

Profile controllers own their error notification; the shared mutation delegates to them without a second toast or banner. If the server write succeeds but updating the local view fails, the notification offers no Retry. Profile editing accepts the submitted value as its confirmed baseline, preserves newer edits and refreshes cached data. The profile flow does not announce success alongside that error or resubmits the known completed write automatically.

Deletion requires a matching signed-in account, email confirmation and a session created within 24 hours. The optional `beforeAccountDelete` extension hook runs before any deletion and may reject the request.

Deletion uses one atomic application-database batch for the user's profile, sessions, linked sign-in accounts, collaborator memberships (including email-only grants), pending invitations to their email and login-code records. Other collaborators remain; their inviter reference is cleared if needed. Repositories, configuration/cache data, contribution history and GitHub App installations stay intact. After confirmation, the browser removes that account's IndexedDB drafts/recent entries and account-scoped project visits, clears its query cache and signs out. Other accounts' local data remains. A local deletion marker prevents older tabs from writing drafts back after cleanup. No GitHub API request is needed. Account's interactive form is separate from its loading component so account deletion and profile controls are not included in the initial page-loading graph.

Authenticated browsers retain an opaque, purpose-scoped HMAC receipt for their own local account data. On return or focus, a browser can check receipts for accounts that are no longer signed in; the server authorizes cleanup only when a receipt is valid and the account no longer exists. A missing session, ordinary sign-out, offline failure or invalid receipt does not authorize deletion. Checks are batched and do not query GitHub. The active authenticated account does not need an existence probe. Receipts grant no authentication, permissions or content access. Cleanup retries after storage/network failures; rotating the installation auth secret invalidates old receipts rather than authorizing a destructive fallback. Browsers that never received a receipt cannot infer prior account deletion.

Successful account deletion redirects to sign-in and displays “Your account has been deleted.” through Sonner. The sign-in page consumes the confirmation flag and replaces its URL, so refreshing does not repeat the message. Failed deletion and reauthentication do not trigger this success notice.

## Account page layouts

Sign in centers the narrow form in the full viewport on desktop and mobile, with the shared 24px About logo at the top left. Its loading component imports only the layout, keeping authentication logic out of the initial bundle. The logo keeps its accessible name and About dialog without a hover tooltip.

Projects, Admin and Account share a transparent 48px header with the About logo on the left and account avatar on the right. It always reserves one row above the content. At widths of 1280px and above, the header sticks to the top while its empty middle allows clicks through to scrolled page content. Below 1280px, it scrolls away with the page, conservatively clearing the 808px Account/Admin column plus the controls and edge spacing. Header horizontal padding is 16px at every screen width. Account and Admin keep their title and small outline chevron back button in the main content, without sticky positioning. Projects centers its content in the remaining space below the header at every width. Loading views use the same header, title and body layout. The login logo retains its About trigger. Profile confirmation continues to omit navigation controls.

Repository sidebar footers show the account avatar on the left and About logo on the right, including loading and mobile views. The top border is visible when the navigation does not overflow or more navigation remains below the current scroll position. It disappears at the bottom of overflowing navigation. Header shadows continue to indicate navigation above the current position. Scroll, viewport resizing and navigation content changes update these boundaries.

GitHub credential fallback applies to lost repository access, not rate limits. Throttling propagates to the caller and never selects or caches collaborator credentials.

OAuth access and refresh tokens are encrypted at rest using AES-GCM with a key derived from `BETTER_AUTH_SECRET`. Account hooks encrypt every token Better Auth writes, and the adapter decrypts on read; any other stored format is rejected. Back up the database and its secret together: changing the secret makes stored tokens unreadable, and users must reconnect.
