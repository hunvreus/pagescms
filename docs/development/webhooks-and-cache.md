# Webhooks and cache

Pages CMS caches configuration and collection/media directory snapshots in PostgreSQL when `.pages.yml` sets `settings.cache: true` (the legacy top-level `cache: true` is normalized too). Directory revision checks default to five minutes (`CACHE_CHECK_MIN`). Complete snapshot expiry defaults to one day (`FILE_TTL_MIN`); `-1` disables that expiry, not revision checks or webhook updates. Fresh snapshots avoid GitHub reads; unchanged revisions avoid content downloads until full snapshot expiry. Cold/stale snapshots are reconciled before the request completes. TanStack Query independently keeps previously loaded client data visible while it refetches.

Media directory snapshots are URL-free manifests. Temporary GitHub or provider URLs are issued separately as authenticated, client-only delivery leases, batched at the directory level, and renewed before expiry or once after an image error. A renewal keeps the previously rendered thumbnail visible until its replacement has loaded. The built-in GitHub provider keeps a bounded, process-local 30-second copy of the authenticated directory response so the manifest and delivery phases share one GitHub request and concurrent consumers coalesce. Authorization runs before this cache can be read, mutations clear it, and it is only an acceleration layer: temporary private URLs are never persisted, SSR-dehydrated, or placed in a public/shared CDN cache.

GitHub entry and media mutations incrementally update eligible directory snapshots; scopes that cannot be patched safely are marked stale for reconciliation. Configuration saves write the normalized configuration through and update affected directory snapshots. Explicit cache-management operations can refresh or clear their scopes. Signed GitHub webhooks cover changes made outside Pages CMS:

- complete small `push` events incrementally update snapshots at the preceding revision using batches of changed files; larger pushes follow the configurable thresholds below. Incomplete/forced events or missing predecessor revisions mark snapshots stale. A complete `.pages.yml` change refreshes normalized configuration during the webhook; an incomplete change list invalidates it for the next read;
- installation and repository removal events clear inaccessible data and tokens;
- repository and installation-account renames migrate cached coordinates, retaining content;
- repository and branch deletion events clear their old scopes;
- `workflow_run` updates tracked action runs.

Configure the GitHub App webhook URL as `https://<host>/api/webhook/github`, content type `application/json`, and the same secret in GitHub and `GITHUB_APP_WEBHOOK_SECRET`. Subscribe to push, delete, installation, installation repositories, installation target, repository, and workflow run events. Invalid signatures return `401`; oversized bodies return `413`; accepted work is processed before a successful response is returned. If webhook volume later requires asynchronous processing, use an explicit durable queue rather than detached request promises.

Private media previews use an authenticated `/api/media-preview/...` endpoint with an ETag and `private, max-age=60, stale-while-revalidate=300`. Do not change this to public caching: the response may contain private repository content.

The portable request-count baseline was captured on 2026-08-28. The legacy public path used one GitHub directory lookup and its private path could use two (the media list followed by the thumbnail URL resolver); both kept a 30-second browser cache. The provider split initially made two lookups for every cold media page. The browser regression test now proves one cold GitHub directory lookup for manifest plus leases and zero on an immediate warm reload.

Run `pnpm test:e2e:media-performance` for the production-preview baseline. It builds the application with the deterministic GitHub fixture, measures first useful render when both thumbnails report `data-state="loaded"`, and covers public and private repository paths. Each p50/p95 is based on 20 full-document samples. Cold samples use distinct uncached directories; warm samples reload the same directory and assert that the process-local directory cache avoids GitHub entirely. The 2026-08-28 local baseline was:

| Repository path | Cold p50 | Cold p95 | Warm p50 | Warm p95 | GitHub directory requests    |
| --------------- | -------: | -------: | -------: | -------: | ---------------------------- |
| Public          |   179 ms |   371 ms |   188 ms |   308 ms | 1 per cold directory; 0 warm |
| Private         |   201 ms |   325 ms |   174 ms |   296 ms | 1 per cold directory; 0 warm |

These numbers remove development compilation from the measurement but are not a substitute for deployed network timings. Record authenticated deployed p50/p95 after the branch is deployed; browser location, GitHub latency, and the selected runtime still affect that result.

If external changes look stale, use the repository Cache page to refresh or clear the relevant scope. A cleared snapshot is repopulated on the next request.

## Legacy cache behavior audit

Sources checked: `_legacy/lib/github-cache-file.ts`, `github-cache-folders.ts`, `github-cache-meta.ts`, `config-store.ts`, `github-image.ts`, `github-cache-permissions.ts`, both webhook handlers, and the file save/delete/rename, collection, reference, media, and cache-management routes. This comparison covers reads and CMS writes, not only pushes.

| Path                              | Current behavior and rationale                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Collection listing and references | Both use the directory cache. Raw file text, SHA, size and paths are persisted. Legacy also parsed content for collection responses; it did not persist a separate parsed document per file.                                                                                                                                                                            |
| Entry/file create and save        | Reuses submitted source and returned blob SHA to patch verified listings; no content redownload.                                                                                                                                                                                                                                                                        |
| File delete                       | Removes the affected cached entry and advances eligible scope revisions; ancestors reconcile.                                                                                                                                                                                                                                                                           |
| Rename and move                   | Reuses the source row only when its blob SHA and verified snapshot match the mutation's base. Supports cached destinations across folders; otherwise batches the missing content.                                                                                                                                                                                       |
| Media upload and folder creation  | Reuses submitted bytes/metadata or the empty `.gitkeep` result. Media rows store metadata only. Binary uploads do not become decoded text in colocated collection rows.                                                                                                                                                                                                 |
| Collection/media colocation       | Media listings can reuse a fresh collection snapshot, stripping text and nested node enrichment. A media-only snapshot cannot satisfy a collection's text requirement. Temporary delivery URLs still require their separate authenticated lease lookup.                                                                                                                 |
| Nested collection node files      | Kept out of parent snapshots. Reuses verified child-directory rows at the same revision; missing nodes are fetched in batches of 50. Changing the configured node filename does not reuse the previous enrichment.                                                                                                                                                      |
| Configuration saves               | Writes normalized submitted configuration through to PostgreSQL. Cache failures do not turn a successful GitHub commit into a failed save.                                                                                                                                                                                                                              |
| Configuration pushes              | Removes stale config then repopulates from the current branch for complete pushes, including deletion handling; delayed deliveries do not intentionally fetch historical config.                                                                                                                                                                                        |
| Freshness controls                | Restored `CACHE_CHECK_MIN=5`, `FILE_TTL_MIN=1440` / `-1`, and `CONFIG_CHECK_MIN=5` (including `CFG_CHECK_MIN` / `CONFIG_CHECK_TTL` aliases).                                                                                                                                                                                                                            |
| Branch/repository reads           | Restored bounded 15-second read caches and in-flight coalescing (`BRANCH_HEAD_TTL_MS`, `REPO_META_TTL_MS`). Credential fingerprints isolate callers. Mutation/webhook checks use uncached branch reads; mutations invalidate acceleration caches.                                                                                                                       |
| Push work limits                  | Restored `WEBHOOK_PUSH_INCREMENTAL_MAX_FILES=120` and `WEBHOOK_PUSH_SCOPED_INVALIDATION_MAX_FILES=800`; zero disables a limit. Above 120 paths, mark affected scopes stale; above 800, mark the branch stale. A direct incremental synchronization of 1,000 files uses 20 GraphQL batches, but **the default webhook policy does not run that synchronization inline**. |
| Repository/account renames        | Moves cache coordinates instead of deleting content. Destination rows win on collisions/replayed events. Access removals, transfers, repository deletion and branch deletion still clear affected caches.                                                                                                                                                               |
| Manual cache operations           | Reconcile, explicit clear, permission clear and configuration refresh/clear remain available. Explicit reconciliation bypasses the process-local head cache.                                                                                                                                                                                                            |
| Failed refresh                    | Retains rows and records a safe error status; an obsolete failing refresh cannot overwrite a newer publication.                                                                                                                                                                                                                                                         |

### Intentional differences

- **Retain stale rows rather than destructive invalidation.** They are not eligible as fresh snapshots, but reconciliation can preserve unchanged data/IDs and avoid unnecessary writes. Explicit administrative clears still delete data.
- **Await refresh work rather than legacy's detached `void ensureFileCacheFreshness(...)`.** Detached request work is unreliable on Workers. The client query cache retains visible data during revalidation; server-side expired reads may incur latency. Deployed latency remains a measurement requirement, not an assumed improvement.
- **Revision equality and publication guards instead of commit-time ordering.** Commit timestamps do not establish ancestry, especially with force pushes. Downloads occur outside database locks; writes publish atomically. The legacy metadata `commit_timestamp` is used for a directory's last full snapshot validation time, not to order Git commits.
- **No durable private download URLs.** Existing authenticated, client-only delivery leases preserve directory batching, browser reuse and renewal without persisting temporary bearer capabilities in PostgreSQL or SSR payloads.
- **No restoration of legacy's one-hour positive permission shortcut.** It could serve cached private content after upstream access was revoked. Repository access uses credential-scoped metadata checks (15-second default) and request-level deduplication instead; this intentionally trades more checks for a shorter revocation window. `PERMISSIONS_TTL_MIN` and its legacy aliases therefore do not control authorization now.
- **Separate collection/media row contexts.** Media refreshes do not overwrite content-bearing rows. Shared reads avoid an unnecessary second manifest lookup; no claim is made that this reduces storage in every colocated setup.
- **Empty snapshots stay cached.** Git does not track empty directories; repeatedly fetching a verified missing/empty configured directory provides no additional information before a revision change or expiry.

Functional coverage is in `tests/integration/database.test.ts`, `src/server/github-api.test.ts`, `src/server/repository-read-cache.test.ts`, and the media/cache unit tests. Production latency, database-write volume and cross-instance contention still require workload measurement; passing these tests is not evidence of production performance parity.

Configuration refreshes also use snapshot-conditional publication: a delayed fetch or 404 cannot overwrite or delete a configuration saved while that request was in flight.
